01SLURM in one minute

  • The cluster is shared. You don't run things directly: you ask SLURM for cores, memory and time, and it queues your job until they are free.
  • Ask for what you need, not the most you can get. A job that goes over its memory or time is killed, and what you reserve but don't use is blocked for everyone else.
  • Measure on a small run first, then scale up from the real numbers.
  • Split the work into independent pieces (one per seed or replicate), one core each. That scales almost linearly.
  • Give jobs names that say what they are, so the queue tells you the story.
  • An agent will fill the node if you let it. It works toward its target, not toward your colleagues, so write the limits down.

01The limits we gave the agent

Jobs at onceAt most 6; drop to 3 if colleagues' jobs are waiting. One in, one out: a new job only after a finished one has been read and recorded.
MemoryStart at 32 GB. If a job runs out of memory, retry at 64 GB, then 96 GB. Never more: record it and move on.
TimeMeasured time plus a margin, set per run type once the first jobs showed the real times.
Stuck jobsNo progress for twice the expected time, or queued for over 6 h: cancel it, record it, resubmit once.
DiskCheck free space before each batch; stop submitting below a set threshold.
DeadlineNo new submissions after Monday 06:00, so everything finishes before people need the node.

Written in the plan file the agent rereads at every wake-up. Anything outside it goes to a FLAGS file for the human.

02Restartability

A run takes hours. When something fails near the end, you want to restart from the last good point, not from scratch.

1 · Build inputs Savedeach pipeline step's result, then the finished input folder If it failsonly the broken step reruns
2 · Simulate Savedone output folder per replicate If it failsrerun only the missing replicates; add more later
3 · Check Saveda pass/fail line in the status log Howfrom the outputs (last record written), not the exit code
4 · Report Savedsummary tables, before any plotting If it failsa plot error costs minutes, not the 2.5 h run
  • Each step leaves a "done" marker. Resubmit the same job and it skips straight to the step that failed.
  • Never overwrite earlier results: additions go next to them.
  • Never edit a script while a job is running it: R and bash read it as they go.

03Supervision: closing the laptop

Claude in Positron's panel stops when the laptop closes. Claude in tmux on the server keeps going.

1ssh sequoiaLog in to the server. Everything from here runs there, not on your laptop.
2tmux new -s calibOpen a terminal that lives on the server and keeps running after you disconnect.
3cd ~/project
claudeStart Claude in the project. Auto mode ("defaultMode": "auto" in .claude/settings.local.json) means it doesn't stop to ask while you're away. The rules in the same file limit what it can touch (section 04).
4/loop Read the plan,
then follow it ...Give it a task to repeat on its own. It wakes up every 20–60 min to check on the jobs.
5Ctrl-b, then dDetach: tmux keeps running. Close the laptop.
6tmux attach -t calibCome back any time: the session is as you left it, and you can type to it.

On sequoia, claude comes with Positron's extension: ~/.positron-server/extensions/anthropic.claude-code-*/resources/native-binary/claude

03Supervision: while you're away

At every wake-up, Claude:

  1. Rereads the plan: targets, limits, what needs you.
  2. Checks the queue: which jobs finished, failed or are still running.
  3. Reads finished results and writes them in the journal.
  4. Decides: submit the next run within the limits, or flag it for you.
  5. Picks the next wake-up and goes idle. Waiting uses no usage.

Hit the session usage limit?

The jobs keep running. Claude waits in the open session and continues on its own when the limit resets. Claude Code v2.1.234+ with a claude.ai plan; sequoia has 2.1.300.

Where it stops

A weekly limit (resets days away) or a third hit in a row: it waits for you. A /loop also expires after 7 days. Don't open the same conversation elsewhere with --resume: two copies act on it.

You read the journal: newest first, every decision with its numbers and job ids, a status summary every few hours.

04Guardrails: layers

LayerExampleGap
The written plan"At most 6 jobs." "Anything outside these rules goes to FLAGS.md, not into action."Relies on the agent following it
Permission rulesIn .claude/settings.local.json: may write the journal, may not write the data folders (next slide)Command rules match the start of the text: /usr/bin/git push slips past
HookA script run before every command: git commit / push only if the current branch is calib_autopilotOnly as good as its pattern (slide after next)
GitHubBranch protection on main: changes only through a pull request you reviewNone: holds however git is called
FilesystemRaw data folder read-only for the account Claude runs as (chmod -R a-w data/raw)Blocks you too, until you undo it
DeletionsA cleanup script: its dry run lists what would go (140 old folders, 21 GB); only --delete removes themYou review the list before it runs

The Bash sandbox (bubblewrap) would confine writes and network, but isn't installed on sequoia.

04Permission rules: the DISPLACE example

Read

the project folder (where Claude starts)

the data tree on the share

the model's source ~/displaceR

other folders: not granted (but a shell command like cat can still read them)

Write

the plan, the journal, params.csv

pipeline code r/**

its own rules: RUNBOOK.md, AUTOPILOT.md

run scripts, renv.lock, the model source

every data folder on the share: raw, inputs, outputs, results

Run

squeue, sacct, sinfo, Rscript

sbatch --job-name=calib_*

git commit, git push origin calib_autopilot

git checkout, reset, push --force, push to main

rm -rf, pkill, sudo

  • Deny beats allow, and a deny still blocks in auto mode.
  • The rules cover Claude, not the jobs it starts. Claude can't write to the output folders, but the SLURM jobs it submits do.

04Guardrails: test them

Feed the hook sample commands before relying on it:

echo '{"tool_input":{"command":"git push origin main"}}' | ./branch-guard.sh; echo $?
git commit -m "add seeds"allowed
git push origin mainblocked ✓
git commit -m "reset seeds"blocked ✗
git commit -m "fix main loop"blocked ✗
  • The pattern reads the commit message too: "reset" and "main" trip it.
  • It errs toward blocking, which is the right side, but test the harmless cases as well as the dangerous ones.

05Data on Nextcloud

On the server, the Nextcloud project folders are the storage. There's no copy to keep in sync.

From a laptop

The Nextcloud app keeps a local copy. Files have to download before a run can read them, and results have to upload before anyone else sees them. That means gigabytes, and waiting.

From the server

Claude and the SLURM jobs read inputs and write results directly where Nextcloud keeps them. A result written at 3 am is in the shared folder at 3 am, and your laptop's Nextcloud app picks it up from there.
  • Point it there with instructions: the plan file says which folders to read from and write to.
  • It's shared, so the guardrails matter: raw data protected, results never deleted, old versions kept next to corrected ones.
  • Network storage can stall for minutes. A slow ls isn't a failure.

Takeaways: why, and what it takes

Advantages

  • Work goes on overnight and over the weekend, with nobody at the keyboard.
  • The cluster does the heavy lifting: six versions in parallel, not one at a time on a laptop.
  • Results land straight in the shared folder. No copying or syncing.
  • Every decision is written down with its numbers, so you can audit the run afterwards.
  • Each step is resumable, so a failure costs minutes, not the run.

Safety concerns, and how we dealt with them

  • It acts without asking. → Written limits, deny rules, a branch hook, GitHub protection.
  • The node and storage are shared. → Job caps, backing off for colleagues, disk checks, a deadline.
  • Some actions can't be undone. → No deleting; dry-run scripts a human approves.
  • It chases the target. → Principles stated up front; anything else goes to a FLAGS file.
  • The rules aren't airtight. → Several layers, each one tested.

Takeaways: what Claude managed on its own

Handled by itself

  • Ran the loop for days: submitted jobs, read results, chose the next version, recorded it.
  • Dozens of calibration versions, within the job and memory limits.
  • Recovered from failures: out-of-memory kills, missing packages.
  • Picked up after losing context by rereading the plan and the journal.
  • Kept the journal and the results table up to date for you to read.

Still needed you

  • Setting the goal, the targets and the principles.
  • Decisions outside the rules (it flagged them and waited).
  • Checking explanations: several first explanations were corrected once checked against the data.
  • Deleting anything, and merging to the main branch.

Next: one skill for all of this?

A skill packages instructions and templates that Claude loads when the task matches. Ask for "a long run on the cluster" and it brings these practices with it.

What the skill would do

  • Ask the few things only you know: goal and targets, limits, deadline, which folders are off limits.
  • Write the plan, the journal and the permission rules from templates.
  • Build restartable job scripts with status lines and "done" markers.
  • Check the node and test its own guardrails before the first job.
  • Give you the exact tmux and /loop steps to start, leave and come back.

What you'd still do

  • Answer its questions and review the plan.
  • Decide on what it flags.
  • Approve deletions and merges.

Worth it?

  • The raw material exists: the playbook was written to be generic, with 7 templates.
  • It pays off once several projects run long jobs on GRIT.
  • It needs upkeep as Claude Code and the cluster change.
